## Setup, measured 2026-11-09

The script printed by `newton-ad-setup write samba` was run as root on the Samba PDC
`sdc1.lab2.newton.test` (Samba 4.22.11). It stopped at step 0 on every run, and the delegation
helper read against the same DC showed the defects below. Every output quoted here was measured on
that DC.

- `samba-tool domain info 127.0.0.1` prints NO `Realm=` line. It prints:
  ```
  Forest           : lab2.newton.test
  Domain           : lab2.newton.test
  Netbios domain   : NEWTONLAB2
  DC name          : sdc1.lab2.newton.test
  DC netbios name  : SDC1
  Server site      : Default-First-Site-Name
  Client site      : Default-First-Site-Name
  ```
  The realm of that domain is the `Domain` line, uppercased. The realm is read with
  `samba-tool testparm --parameter-name=realm --suppress-prompt`; that command was NOT measured on
  this DC, so the script falls back to the `Domain` line when it prints nothing.
- `ldbsearch -H sam.ldb --scope=base '' dsServiceName` takes `''` as the FILTER: it searches the
  domain head, which holds no `dsServiceName`, so the PDC check never passes. The rootDSE is read
  with `ldbsearch -H sam.ldb -b '' --scope=base '(objectClass=*)' dsServiceName`, and it answers:
  ```
  dn: 
  dsServiceName: CN=NTDS Settings,CN=SDC1,CN=Servers,CN=Default-First-Site-Name,
   CN=Sites,CN=Configuration,DC=lab2,DC=newton,DC=test
  ```
- ldbsearch folds a long value onto the next line, and the continuation line starts with ONE space.
  The `fSMORoleOwner` of the domain head folds the same way, so every read of ldbsearch has to
  unfold the LDIF before it reads a value.
- The line of the GUID of a schema object is `schemaIDGUID: <guid>`. A class and an attribute are
  both named by their display name: `(lDAPDisplayName=userAccountControl)` answers
  `bf967a68-0de6-11d0-a285-00aa003049e2`, and the class `user` answers
  `bf967aba-0de6-11d0-a285-00aa003049e2`.
- **An ACE with GUIDs must be of type `OA`.** `samba-tool dsacl set --sddl
  "(A;CI;0x00000020;bf967a68-...;bf967aba-...;<sid>)"` returns 0 and DROPS the GUIDs: it stores
  `(A;CI;WP;;;LG)`, which is a write on every property of every object below. The same ACE with the
  type `OA` stores `(OA;CI;WP;bf967a68-0de6-11d0-a285-00aa003049e2;bf967aba-0de6-11d0-a285-00aa003049e2;LG)`.
- The rights that replicate the directory are `controlAccessRight` objects under
  `CN=Extended-Rights,CN=Configuration,DC=lab2,DC=newton,DC=test`, NOT objects of the schema, and
  a search of the schema finds nothing at all. The attribute is `rightsGuid`:
  `ldbsearch -b "CN=Extended-Rights,CN=Configuration,DC=lab2,DC=newton,DC=test"
  "(name=DS-Replication-Get-Changes)" rightsGuid` answers `rightsGuid: 1131f6aa-9c07-11d1-f79f-00c04fc2dcd2`.
  The domain head holds `(OA;;CR;1131f6aa-9c07-11d1-f79f-00c04fc2dcd2;;BA)`,
  `(OA;;CR;1131f6ad-9c07-11d1-f79f-00c04fc2dcd2;;DD)` and `(OA;;CR;1131f6aa-9c07-11d1-f79f-00c04fc2dcd2;;ED)`,
  among others.
- `samba-tool dsacl get --objectdn X` prints a first line `descriptor for X:` and then the SDDL.
  `samba-tool dsacl set` prints `old descriptor for ...:` and `new descriptor for ...:` blocks: they
  are never parsed, the descriptor is read back with `dsacl get`.
- `dsacl get` prints the access masks as letters (`WP`, `CR`, `CCDC`) and the well known SIDs as
  names (`LG`, `DU`, `BA`, `ED`, `DD`), so a descriptor is never compared as text. Samba parses it:
  ```
  from samba.dcerpc import security
  d = security.descriptor.from_sddl(sddl, security.dom_sid(domain_sid))
  a = d.dacl.aces[0]   # a.type 5 (ACCESS_ALLOWED_OBJECT), a.flags, a.access_mask 0x20,
                        # str(a.trustee) 'S-1-5-21-...-513', a.object.flags 3,
                        # str(a.object.type), str(a.object.inherited_type)
  ```
  The domain SID is the SID of `newton-ops` without its last component, and it is the SID the well
  known names of a descriptor are resolved against.

## Windows setup, measured 2026-11-09

The script printed by `newton-ad-setup write windows` was run as Administrator on the real Windows
Server 2025 PDC `WSBXDC1.win2.newton.test`, under Windows PowerShell 5.1. It stopped at step 0. The
facts below were measured on that controller; the steps 2 and 6 were applied by hand with the
commands below and they worked.

- The computer account of the controller is `CN=WSBXDC1,OU=Domain Controllers,DC=win2,DC=newton,
  DC=test`: the OU of the controllers is the PARENT of the account, and not a prefix of its name.
- `Get-ADObject -Filter '(objectClass=...)'` takes the filter language of PowerShell and throws
  `ADFilterParsingException`. The LDAP filter is `-LDAPFilter`.
- `New-ADUser` has no `-UserAccountControl` ("A parameter cannot be found that matches parameter
  name 'UserAccountControl'"), and it returns nothing without `-PassThru`.
- `Get-ADUser` without `-Properties userAccountControl` answers no `userAccountControl` at all.
- The GUIDs of the schema are keyed by the LDAP display name. The name of the attribute is its CN
  (`User-Account-Control`) and the display name is the one the directory uses (`userAccountControl`).
  The class `user` is `bf967aba-0de6-11d0-a285-00aa003049e2` and the attribute
  `userAccountControl` is `bf967a68-0de6-11d0-a285-00aa003049e2`.
- **`dsacls` takes a SID as the trustee, and every argument is its own element of the argument
  array.** These forms work:
  - `dsacls <OU> /I:S /G "<SID>:WP;<lDAPDisplayName>;<class>"` stores
    `(OA;CIIO;WP;<attr guid>;<class guid>;<SID>)`. It is the form of the ten property rights.
  - `dsacls <OU> /I:T /G "<SID>:CCDC;user"` stores `(OA;CI;CCDC;<user guid>;;<SID>)`. The same
    form serves `computer`, and it grants the create-child and the delete-child right in ONE ace.
  - `dsacls <domain DN> /G "<SID>:WP;ms-DS-MachineAccountQuota"` (no `/I`) stores a WriteProperty
    on `d064fb68-1480-11d3-91c1-0000f87a57d4`, with the inheritance `None`.
  - The result is 12 aces per OU and one on the head of the domain. `dsacls <dn> /add <ace>` is
    not a form of dsacls: it answers 87.
- **The rules of an object are read as objects, and not as SDDL text.**
  `(Get-ADObject <dn> -Properties nTSecurityDescriptor).nTSecurityDescriptor.GetAccessRules($true,
  $false, [System.Security.Principal.SecurityIdentifier])` answers rules with these fields:
  - `ActiveDirectoryRights`: `WriteProperty`, or `CreateChild, DeleteChild`;
  - `ObjectType`, a GUID;
  - `InheritedObjectType`, a GUID, or all zeros;
  - `InheritanceType`: `Descendents` for `/I:S`, `All` for `/I:T`, `None`;
  - `ObjectFlags`: `ObjectAceTypePresent, InheritedObjectAceTypePresent`;
  - `IdentityReference.Value`, the SID.
  `GetSddlForm` prints the masks as letters (`WP`, `CCDC`) and the well known SIDs as names (`LG`),
  so a comparison of that text never matches.
- **The SeBatchLogonRight of the Default Domain Controllers Policy.** The recipe that worked:
  1. `Backup-GPO -Guid 6AC1786C-016F-11D2-945F-00C04fB984F9 -Path <dir>`.
  2. `Get-ADObject -Identity "CN={<guid>},CN=Policies,CN=System,<domain>" -Properties
     versionNumber,gPCFileSysPath`. The object is of the class `groupPolicyContainer`.
  3. The template is `<gPCFileSysPath>\Machine\Microsoft\Windows NT\SecEdit\GptTmpl.inf`, and it
     is UTF-16LE with a BOM (`ff fe`). It starts with `[Unicode]` / `Unicode=yes` and it holds a
     `[Privilege Rights]` section with the line
     `SeBatchLogonRight = *S-1-5-32-559,*S-1-5-32-551,*S-1-5-32-544`. It is read with
     `[IO.File]::ReadAllLines($t, [Text.Encoding]::Unicode)` and written with
     `New-Object Text.UnicodeEncoding($false, $true)`: the first bytes stay `ff fe 5b 00`.
  4. The `Version=` of `<gPCFileSysPath>\GPT.INI` (ASCII) goes up by one, and so does the
     `versionNumber` of the policy object.
  5. `gpupdate /target:computer /force`.
  6. `secedit /export /areas USER_RIGHTS /cfg <file> /quiet`. Its line reads
     `SeBatchLogonRight = newton-ops,*S-1-5-32-544,*S-1-5-32-551,*S-1-5-32-559`: secedit prints the
     NAME of an account and the SID of a well known one, so every holder is resolved into a SID.
- **The install root `C:\ProgramData\Newton\ad` keeps the rules it inherits from ProgramData**, and
  one of them is the write of `BUILTIN\Users`: any local user may add files beside the helper, and
  the helper of the write path answers `denied` to every request because of it. The fix that worked
  is `icacls <root> /inheritance:r /grant:r *S-1-5-18:(OI)(CI)F *S-1-5-32-544:(OI)(CI)F
  *<ops SID>:(RX)`, where the grant of the write account applies to the folder itself only, plus
  `*<ops SID>:(R)` on `device.txt`.

## Windows setup, measured 2026-11-09, sixth run

The Windows script printed by that build (the network-credential pre-check and the share of the PDC's own
SYSVOL, the grant of the right of a password reset to the CREATOR OWNER, and the lookup of that right by its CN
checked by its display name and its GUID, with the Windows write helper merged in, so `write.ps1` was there) was run
as Administrator on the real Windows Server 2025 PDC `WSBXDC1.win2.newton.test`, under Windows PowerShell 5.1, OVER AN
SSH KEY LOGIN. The session is an S4U logon: `klist` shows `Cache Flags: 0x4 -> S4U`. It ran to the end:

- the step 0 printed "This session can read the share of the PDC.";
- 27 ACEs were present;
- the step 6 backed the policy up, granted the right (the version of the policy went to 8) and
  verified it with secedit.

Measured in that key session:

- `\\WSBXDC1.win2.newton.test\SYSVOL\win2.newton.test\Policies\{6AC1786C-016F-11D2-945F-00C04fB984F9}\GPT.INI`:
  read OK.
- `Backup-GPO -Server WSBXDC1.win2.newton.test`: OK.
- the `GptTmpl.inf` of the share of the PDC, opened for write: OK.
- `\\WSBXDC2.win2.newton.test\SYSVOL\win2.newton.test\Policies\{6AC1786C-016F-11D2-945F-00C04fB984F9}\GPT.INI`:
  FAIL, "Cannot find path ... because it does not exist".

**The rule.** An S4U session reaches the SYSVOL share of the controller it runs on, and not the
share of another controller. The share of the name of the domain may be served by another
controller, and the share of the PDC is the one that holds the policy of the PDC. The earlier
failing measurement of the third run failed for that reason, and not because a key login cannot
back the policy up: that run used the share of the name of the domain, and that share was served
by `WSBXDC2`. The script of that build uses the share of the PDC, and the key login on the PDC runs
the whole setup to the end.

**This rule is too strong: see the seventh run.** It is true for the reads of the files of the
share, and it is false as a promise about `Backup-GPO`: over an S4U session the read of the
GPT.INI answers and the backup of the policy fails.

## Windows setup, measured 2026-11-09, seventh run

The Windows script printed by that build (the transaction-record and confirm-flow fixes of the Samba write helper
and the base read of the account's groups of the Windows setup merged in, so `write.ps1` was there) was run as
Administrator on the real Windows Server 2025 PDC `WSBXDC1.win2.newton.test`, under Windows PowerShell 5.1, OVER AN
SSH KEY LOGIN. The session is an S4U logon: `klist` shows
`Cache Flags: 0x4 -> S4U`. The step 0 printed "This session can read the share of the PDC.", the
steps 1 to 5 completed, and the step 6 stopped:

```
Backup-GPO : Access is denied. (Exception from HRESULT: 0x80070005 (E_ACCESSDENIED))
```

Right after, in the same kind of key session, measured:

- the GPT.INI read of the share of the PDC: OK;
- opening `GptTmpl.inf` for write: OK;
- `Backup-GPO -Server <PDC>`: FAIL, E_ACCESSDENIED;
- `Backup-GPO` without `-Server`: FAIL;
- `\\win2.newton.test\SYSVOL`: Access is denied.

The same step 6 code passed over a key login earlier the same day (the sixth run above). So over
an S4U session `Backup-GPO` is unreliable, and the read of the GPT.INI of the step 0 does not
predict it: the step 0 read the file and called the session good, and the run stopped at the
step 6 with the account created and the delegation granted.

**The rule of the share check is too strong.** The sixth run said that an S4U session reaches the
SYSVOL share of the controller it runs on, and not the share of another controller. That is true
for the reads of the files, and it is false as a promise about `Backup-GPO`. A session that reads
the share of the PDC may not be able to back the policy of the PDC up.

**What the setup does now.** The step 0 takes the backup of the policy itself, before
the step 1, into a folder named after the time of the run; the step 6 uses that backup and takes
no other one. A run that cannot back the policy up stops in the step 0, and the domain is as it
was. The run needs a session with network credentials: an interactive logon, or a remote logon
made with a password.
